# Формат внешних обработок (.ert) и их создание/редактирование через MCP

Этот документ описывает бинарный формат файлов внешних обработок 1С:Предприятие
7.7 (`*.ert`), реверс-инжиненный на основе образцов в `work/ExtForms/*.ert`
(единственный доступный источник — официальной документации формата нет), а
также новые MCP-инструменты для создания и редактирования таких файлов.

**Важная оговорка.** Ни на одном этапе разработки не было доступного
экземпляра 1С:Предприятие 7.7 для проверки. Всё нижеописанное верифицировано
только через:
- библиотеку `olefile` (единственный независимый читатель контейнера в этом
  проекте) — round-trip запись/чтение;
- побайтовое и структурное сравнение с реальными образцами `.ert`;
- собственный парсер `bracket_parser.py`, который тоже реверс-инжинирен.

Если сгенерированный `.ert` когда-нибудь не откроется в реальном 1С 7.7 —
начинать разбор стоит именно с ограничений, перечисленных ниже.

## 1. Обзор

Файл `.ert` — это отдельный (standalone) объект "внешняя обработка/отчёт" 1С
7.7. Технически это **тот же самый контейнер OLE2/CFBF (Compound File Binary
Format)**, что используется и для основного файла конфигурации `1Cv7.MD`, и
для форм/модулей объектов внутри него — просто с одним объектом на корне,
без иерархии `Config/Catalog_NumberXXX/...`.

## 2. Структура контейнера (MS-CFB)

Параметры, которые 1С 7.7 использует для `.ert` (подтверждено на образцах):

| Параметр | Значение |
|---|---|
| Sector size | 512 байт (`sector shift` = 9) |
| Mini sector size | 64 байта (`mini sector shift` = 6) |
| Mini stream cutoff | 4096 байт |
| Major version | 3 |
| Minor version | 0x003E |

Все 7 потоков `.ert` лежат прямо на корне контейнера (root storage), без
вложенных под-хранилищ:

```
Container.Contents
Container.Profile
Dialog Stream
Inplace description
MD Programm text
Main MetaData Stream
Page.1
```

Директории (directory entries) в реальных файлах отсортированы по правилу
`CompareDirectoryEntryName` из спецификации MS-CFB: сначала по длине имени,
затем регистронезависимо по алфавиту:

```
Page.1 (6) < Dialog Stream (13) < MD Programm text (17)
< Container.Profile (18) < Container.Contents (19)
< Inplace description (20) < Main MetaData Stream (21)
```

### Известные ограничения писателя (`ole_writer.py`)

- **Балансировка красно-чёрного дерева не реализована.** Спецификация
  требует red-black tree по именам записей, но `olefile` (единственный
  читатель, доступный для проверки) не валидирует цвета/баланс — только
  проходит по указателям `left`/`right`/`child`. Писатель строит простое
  бинарное дерево поиска по отсортированным именам (гарантирует корректный
  порядок обхода), без настоящей RB-балансировки/раскраски.
- **DIFAT-цепочка не реализована.** При количестве секторов таблицы FAT
  больше 109 (то есть суммарный объём файла выше ~7 МБ) `write_compound_file`
  бросает `NotImplementedError` вместо генерации DIFAT-секторов. `.ert`-файлы
  этого проекта (десятки–сотни КБ) никогда не приближаются к этому порогу.
- Ни то, ни другое не проверено на реальном 1С 7.7 — только на `olefile`.

## 3. Потоки .ert

| Поток | Назначение | Кодирование | Редактируется через MCP |
|---|---|---|---|
| `Container.Contents` | Список из 5 подкомпонентов объекта (метаданные/диалог/модуль/описание/Moxcel-лист) с их именами и ролями | Текст, `{...}`-скобки, БЕЗ заголовка длины (начинается сразу с `{`) | Нет — фиксированный шаблон (одинаков во всех образцах) |
| `Container.Profile` | Служебные поля Moxcel + поле `UUID` | Текст, `{...}`-скобки, без заголовка | Нет — фиксированный шаблон (см. врезку ниже) |
| `Dialog Stream` | Форма (диалог) — окно, элементы управления | Текст, `{...}`-скобки, заголовок `0xFF` + 2 байта LE-длины + windows-1251 | Да — через структурную модель `Dialog` |
| `Inplace description` | Свободное текстовое описание | Непрозрачный blob (`\x03\x00` в образцах) | Нет — фиксированный шаблон |
| `MD Programm text` | Программный модуль (БСЛ) | raw-deflate (`zlib`, wbits=-15) сжатый windows-1251 текст, без заголовка | Да — полная замена текста |
| `Main MetaData Stream` | Полная копия словаря метаданных конфигурации на момент экспорта (та же грамматика, что и `metadata.py` разбирает для `1Cv7.MD`) | Текст, `{...}`-скобки, заголовок `0xFF` + 2 байта LE-длины | Нет — фиксированный шаблон (см. §6) |
| `Page.1` | "MOXCEL"-лист (печатная форма) | Бинарный, свой формат (`MOXCEL`-магия), см. §10 | Да, ограниченно — простая сетка текста (см. §10) |

### `Container.Profile.UUID` — НЕ генерировать заново

Поле `UUID` внутри `Container.Profile` выглядит как идентификатор объекта,
но во **всех** образцах корпуса (`work/ExtForms/*.ert`, сотни файлов) оно
содержит один и тот же литерал `D41D8CD98F00B204E9800998ECF8427E` (hex MD5
пустой строки в верхнем регистре — судя по всему, служебный сентинел "нет
профиля/защиты", а не per-file идентификатор). Ранняя версия `ert_writer.py`
подставляла сюда свежий `uuid.uuid4()` при каждом `create_ert_file`, считая
поле честным UUID. На практике любое отличное от сентинела значение здесь
заставляет 1С 7.7 Конфигуратор считать контейнер защищённым и запрашивать
пароль при открытии (подтверждено методом исключения: побайтовая пересборка
реального `.ert` через наш `ole_writer` открывается нормально; подмена
любого из потоков сгенерированным вариантом ломает открытие, кроме случая,
когда `Container.Profile` возвращён к оригиналу). Исправление: `UUID`
всегда фиксирован, никогда не генерируется заново.

### Формат заголовка текстовых потоков

`ole_reader._strip_header` / `ert_writer._encode_text_with_header`:
- Если поток начинается с `{` (0x7B) — заголовка нет, это чистый текст.
- Иначе: N подряд идущих байт `0xFF`, затем (N+1)-байтное little-endian
  число — длина текста, затем сам текст в кодировке windows-1251. В образцах
  `.ert` (< 64 КБ) N всегда равен 1, то есть заголовок — это один байт `0xFF`
  плюс 2-байтная длина. Писатель поддерживает только этот однобайтовый
  вариант и бросает `ValueError`, если текст превышает 0xFFFF байт (более
  крупные заголовки — 2×0xFF + 3-байтная длина и т.д. — не реализованы, так
  как реальных образцов с таким размером `Dialog Stream` не встречалось).

## 4. Грамматика скобочного формата 1С

Реализована в `bracket_parser.py`, используется и для `Dialog Stream`, и для
`Main MetaData Stream`. Кратко:
- `{значение1,значение2,{вложенный,узел},...}` — узел содержит список
  значений и список дочерних узлов, порядок которых при разборе разделяется
  (позиция значения относительно дочернего узла в исходном тексте не
  восстанавливается автоматически — см. `FRAME_TAB_NODE_HEAD_LEN` в
  `dialog_model.py`, где это учтено явным образом для `Frame`).
- Строковые значения — в двойных кавычках, `""` внутри строки — экранированный
  символ `"`. Практически все значения (в т.ч. числовые на вид) в
  `Dialog Stream`/`Main MetaData Stream` всегда сериализуются в кавычках.
- Значение может само содержать текст `{...}` как экранированную строку
  (не как вложенный узел) — так устроено поле "позиция в группе табуляции"
  контрола формы: `"{""0"",""0""}"`, что после снятия экранирования даёт
  Python-строку `{"0","0"}`. Писатель применяет общую функцию квотирования
  ко всем строковым значениям, поэтому это поле обрабатывается так же, как
  любое другое, без специального случая.

## 5. `Dialog Stream`: справочник полей

```
{"Dialogs",
 {"Frame", {<30 позиционных полей>, {"0", {<имя группы>, <номер группы>}}}},
 {"Controls", {<43 позиционных поля>}, ...},
 {"Cnt_Ver", "10001"}}
```

### Frame (30 позиционных полей)

Полностью понятны и редактируются: `font_name` (индекс 13), `width` (14),
`height` (15), `caption` (16). Остальные 26 полей — геометрия/стиль окна,
наблюдались идентичными во всех образцах; хранятся и переносятся как есть
(`extra` в `DialogFrame`, `dialog_model.py`) без изменений при редактировании.

Вложенный узел группы табуляции `{"0", {"Основной","1"}}` вставляется строго
после 28-го из 30 позиционных значений (`FRAME_TAB_NODE_HEAD_LEN = 28` в
`dialog_model.py`) — это позиция подтверждена побайтовым сравнением с
реальным образцом (`work/ExtForms/1.ert`).

### Controls (43 позиционных поля на каждый элемент)

Число и порядок полей подтверждены одинаковыми для всех классов контролов,
встреченных в `work/ExtForms/*.ert`: `BUTTON`, `STATIC`, `1CEDIT`, `BMASKED`,
`CHECKBOX` (проверено на ~340 контролах из полного корпуса образцов). Классы,
не встретившиеся в образцах (например `TABLE`, `COMBOBOX`, `PICTURE`), не
гарантированно имеют тот же набор полей — при разборе такого контрола
неизвестные позиции просто попадают в `extra` и переносятся как есть.

| Индекс | Поле | Пример |
|---|---|---|
| 0 | caption (подпись) | `"Закрыть"` |
| 1 | control_class (класс) | `BUTTON`, `STATIC`, `1CEDIT`, `BMASKED`, `CHECKBOX` |
| 2 | style_flags (Windows-стиль, десятичное число) | `1342177291` |
| 3–6 | x, y, width, height | `70,142,54,14` |
| 9 | id (уникален в пределах формы) | `4152` |
| 11 | action (обработчик/действие) | `Сформировать()`, `#Закрыть` (стандартная кнопка закрытия) |
| 12 | bound_attribute (привязанный реквизит формы) | `ИД_Задачи_Мегаплана` |
| 14 | type_code (см. §6 — `TYPE_CODES`) | `U`, `S`, `B`, `D`, `O` |
| 15 | length (длина/точность поля ввода) | `11` |
| 41 | tab_group_name (группа табуляции) | `Основной` |
| 42 | tab_group_pos (экранированная строка, см. §4) | `{"0","0"}` |
| остальные (7,8,10,13,16–40) | не разобраны, наблюдались константными во всех образцах | — |

## 7. Стратегия для `Main MetaData Stream` и `Page.1`

`Main MetaData Stream` **всегда копируется байт-в-байт из встроенного
шаблона** (`src/mcp_1c77/templates/main_metadata_minimal.bin`, извлечён из
`work/ExtForms/1.ert`) и никогда не редактируется/не синтезируется через MCP.

Причина: это полная копия словаря метаданных хост-конфигурации на момент
экспорта (нужна 1С для разрешения ссылок на объекты без подключения к живой
базе). Грамматика этого блока большая и сложная (`TaskItem`, `Consts`,
`SbCnts`, `Documents`, `Registers`, `EnumList`, `ReportList`, `Buh`, `CRC` и
т.д. — см. `metadata.py::_parse_configuration`). Собрать корректный
минимальный вариант с нуля рискованно; клонирование реального, заведомо
открывающегося в 1С потока — значительно безопаснее.

**Следствие**: обработка, созданная через `create_ert_file`, содержит
метаданные шаблонного объекта, а не реальной конфигурации сервера. Если
1С-конфигурация валидирует форму/реквизиты обработки против реальных
справочников/документов текущей базы, такие ссылки не разрешатся. Это
приемлемо для основного сценария использования (несложные обработки на БСЛ
с простым диалогом), но стоит иметь в виду.

`Page.1` (MOXCEL-лист/печатная форма), в отличие от `Main MetaData Stream`,
**формат которого реверс-инжинирен и понятен** (см. §10) — по умолчанию
копируется из шаблона (`templates/page1_empty.bin`, пустая таблица без
строк/колонок — тот же результат, что и у `write_moxel` над пустым `MoxelSheet`,
проверено побайтово), но может быть сгенерирован заново из простой сетки
текста через `print_form_rows`/`update_ert_print_form` (§10.4).

## 8. CLI-флаг и MCP-инструменты записи

### `--edit-path <каталог>`

Необязательный параметр запуска (`python -m mcp_1c77 --edit-path <dir>`).
Если указан:
- каталог создаётся при старте, если не существует;
- каталог автоматически добавляется в список сканируемых на `.ert`-файлы
  (наравне с `ExtForms`/`--exts`), поэтому созданные/изменённые файлы сразу
  видны инструментам чтения (`list_ert_files`, `get_ert_module`, ...);
- становятся доступны инструменты записи, перечисленные ниже.

Если флаг не указан — все write-инструменты зарегистрированы (видны в списке
инструментов MCP), но при вызове возвращают текстовое сообщение об ошибке
вместо результата.

### Инструменты записи

Работают **только** с файлами внутри `--edit-path` — резолвинг цели идёт
исключительно по голому имени (`<edit-path>/<name>.ert`), без обращения к
индексу `ErtLoader` по всем каталогам, поэтому одноимённый файл из другого
(read-only) каталога никогда не может стать целью записи.

- `create_ert_file(name, module_text="", caption="", print_form_rows=None)` —
  создать новую обработку с пустой (или заданной) формой, модулем и
  печатной формой. Отказ, если файл уже существует или имя некорректно
  (`/`, `\`, `..`, пусто).
- `update_ert_module(name, new_text)` — полностью заменить текст модуля.
- `set_ert_dialog_frame(name, caption=None, width=None, height=None)` —
  изменить заголовок/размер окна формы.
- `add_ert_dialog_control(name, caption, control_class, x, y, width, height, action="", bound_attribute="", type_code="", tab_group_name="Основной")`
  — добавить элемент управления (id назначается автоматически).
- `update_ert_dialog_control(name, control_id, ...)` — изменить поля
  существующего элемента (только переданные параметры).
- `remove_ert_dialog_control(name, control_id)` — удалить элемент.
- `update_ert_print_form(name, rows)` — заменить печатную форму (`Page.1`)
  простой сеткой текстовых ячеек (см. §10.4).

Дополнительно (доступны всегда, без привязки к `--edit-path`, это
инструменты чтения):
- `list_ert_dialog_controls(name)` — структурированный список элементов
  формы (id, класс, подпись, координаты, привязка, тип, действие) —
  использовать перед добавлением/изменением/удалением элементов.
- `get_ert_print_form(name)` — разобранная печатная форма (непустые ячейки
  по строкам/колонкам), см. §10.5.

**Намеренно не реализовано:**
- Редактирование `Main MetaData Stream`, `Container.Contents`,
  `Container.Profile` через MCP — см. §7.
- Форматирование, объединение ячеек и встроенные объекты (картинки/OLE/
  линии) в `Page.1` — `update_ert_print_form`/`print_form_rows` создают
  только простую сетку текста, см. §10.4.
- Единый инструмент "записать сырой текст Dialog Stream целиком" — только
  через структурную модель (`Dialog`/`DialogControl`), чтобы гарантировать
  сохранность `extra`-полей и синтаксическую валидность.

## 9. Ограничения тестирования

Все автотесты (`tests/test_ole_writer.py`, `tests/test_dialog_parser.py`,
`tests/test_moxel.py`, `tests/test_ert_writer.py`, `tests/test_tools_edit_ert.py`)
проверяют round-trip запись → чтение через `olefile`/`ert_loader`/`ole_reader` —
то есть через тот же самый read-only путь, которым пользуются обычные
MCP-инструменты чтения. Это единственный доступный критерий корректности:
реального 1С:Предприятие 7.7 для сквозной проверки в этом окружении нет.
Для `Page.1`/MOXCEL этот критерий дополнительно усилен массовой проверкой на
всём доступном корпусе реальных файлов (см. §10.3).

## 10. Формат `Page.1` (MOXCEL) — печатная форма

### 10.1. Источник

В отличие от остальных потоков `.ert`, формат MOXCEL не пришлось разбирать
"с нуля" — существует открытый (не аффилированный с 1С) реверс-инжиненный
читатель/писатель на C#: **[v7Moxel](https://github.com/DmitryDreytser/v7Moxel)**
(`v7Moxel/Moxel/Moxel/*.cs`), умеющий читать версии 6 и 7 формата и
экспортировать в Excel/HTML/PDF. Раскладка байт в этом документе перенесена
из его исходников (`CSheetFormat.cs`, `DataCell.cs`, `MoxelRow.cs`,
`LOGFONT.cs`, `Enums.cs`, `CellsUnion.cs`, `Section.cs`, `MoxelArea.cs`,
`EmbeddedObject.cs`, `Picture.cs`, `BinaryReaderExtention.cs`) на Python
(`src/mcp_1c77/moxel_reader.py`/`moxel_writer.py`/`moxel_model.py`).

MOXCEL — это встроенный в 1С 7.7 табличный редактор (похож на упрощённый
Excel), которым верстается **печатная форма** отчёта/обработки — то, что
реально печатается/выводится на экран, в отличие от `Dialog Stream`
(экранной формы ввода параметров).

### 10.2. Структура файла

Заголовок: сигнатура `"MOXCEL"` (6 байт) + 5 нулевых байт, с офсета `0x0B`
(11) — `version:int16` (6 или 7), затем `nColumns/nRows/nObjects:int32`.
Далее последовательность блоков, сериализованных в формате MFC
`CArchive`/`CString` (тот же общий стиль, что и в остальных потоках `.ert`,
но с типизированными бинарными структурами вместо текстовых `{...}`-скобок):

```
DefFormat: DataCell            — формат ячейки по умолчанию для всей таблицы
FontList: словарь LOGFONT      — таблица шрифтов
stringTable: словарь строк     — общая таблица строк (в образцах всегда пуста)
Header, Footer: DataCell       — колонтитулы
Columns: словарь DataCell      — форматные ячейки колонок (в т.ч. ширина)
Rows: словарь MoxelRow         — строки (формат строки + словарь ячеек)
Objects: список EmbeddedObject — линии/прямоугольники/текстовые блоки/картинки/OLE
Unions: список CellsUnion      — объединённые ячейки (4×int32: left,top,right,bottom)
VerticalSections, HorisontalSections: список Section
VerticalPageBreaks, HorisontalPageBreaks: массив int32
AreaNames: список MoxelArea    — именованные области
```
+ 2 нулевых байта в конце файла (наблюдались во всех образцах, назначение
не установлено — вероятно, терминатор `CArchive`).

**`Section`** (`moxel_model.MoxelSection`) — 3×`int32` (`begin`, `end`,
`level`) + `CString name`. Это именованные "секции" печатной формы,
которые 1С-код выводит по имени через `Таблица.ВывестиСекцию("Имя")`,
комбинируя их построчно/поколоночно в итоговый отчёт (типичные имена:
"Шапка", "Строка", "Подвал", "ЗаголовокТаблицы", вложенные группировки
через `level`). `HorisontalSections` — диапазон `begin..end` — это номера
**строк**; `VerticalSections` — то же для **колонок**; `level` — уровень
вложенности группировки (`0` — верхний уровень; вложенные/группируемые
секции реального корпуса используют `1`+). Реально используются в 140 из
339 файлов `work/ExtForms/*.ert` — самая частая и надёжная именно эта
сущность формата (в отличие от `AreaNames` ниже). С 2026-09 доступны
точечные MCP-инструменты для чтения/добавления/изменения/удаления секций
без пересборки всей печатной формы — см. §10.4.

**`MoxelArea`** (`AreaNames`) — `CString name` + 2×`int32` (неизвестные,
первый почти всегда `1`, второй помечен даже в первоисточнике-`v7Moxel`
как "always garbage") + `int32 area_type` + 4×`int32`
(`col_begin/row_begin/col_end/row_end`). **В корпусе `work/ExtForms`
реальных, валидных записей `AreaNames` не найдено** — единственные 3
"находки" (во всех версиях одной обработки «КнигаДоходовИРасходов») —
явный мусор из-за десинхронизации разбора на трейлере файла (см. §10.3),
а не настоящие области. Смысл `area_type` не расшифрован нигде, включая
первоисточник — считайте эту сущность неподдерживаемой/неиспользуемой на
практике; MCP не предоставляет инструментов для неё (не путать с
`Section` выше, который реально используется и поддержан).

**MFC-примитивы**, общие для всех словарей/списков/строк (реализованы в
`moxel_reader.py`/`moxel_writer.py`):
- `count` — `uint16`, если `> 65534` — далее ещё `int32` (для больших
  массивов);
- `int[]` — `count` + столько `int32`;
- `CString` — 1 байт длины; если `0xFF` — далее `uint16`; если результат
  `0xFFFF` — далее `int32`; текст в cp1251;
- словарь `T` — `int[]` ключей, затем ещё раз `count` (избыточно,
  дублирует длину массива ключей — так сериализует сам 1С, читается и
  пишется как есть), затем по одному значению `T` на каждый ключ по порядку;
- список `T` — `count` + `T` подряд.

**`CSheetFormat`** (`moxel_model.CellFormat`) — 30-байтная структура
(`Pack=1`) на каждую ячейку/строку/колонку/колонтитул:

| Офсет | Поле | Смысл |
|---|---|---|
| 0x00 | `dwFlags` (`uint32`) | Битовые флаги — какие поля вообще заданы (см. ниже) |
| 0x04 | `w1` (`int16`) | `wHeight` (строки) / `wShow` (колонтитулы) / не используется (колонки) |
| 0x06 | `w2` (`int16`) | `wWidth` (колонки) / `wStartPage` (колонтитулы) / не используется (строки) |
| 0x08 | `wFontNumber` (`int16`) | Индекс в `FontList` |
| 0x0A | `wFontSize` (`int16`) | Размер шрифта |
| 0x0C | `bFontBold` (`byte`) | `0`=не задан, `4`=обычный, `7`=жирный |
| 0x0D | `bFontItalic` (`bool`) | |
| 0x0E | `bFontUnderline` (`bool`) | |
| 0x0F | `bHorAlign` (`byte`) | `0`=слева,`2`=справа,`4`=по ширине,`6`=по центру |
| 0x10 | `bVertAlign` (`byte`) | `0`=сверху,`8`=снизу,`0x18`=по центру |
| 0x11 | `bPatternType` (`byte`) | Тип заливки |
| 0x12–0x15 | `bBorderLeft/Top/Right/Bottom` (`byte`×4) | Стиль границ (см. `BorderStyle`) |
| 0x16 | `bPatternColor` (`byte`) | Индекс в палитре (`PALETTE`, 56 цветов) |
| 0x17 | `bBorderColor` (`byte`) | Индекс в палитре |
| 0x18 | `bFontColor` (`byte`) | Индекс в палитре |
| 0x19 | `bBackground` (`byte`) | Индекс в палитре |
| 0x1A | `bControlContent` (`byte`) | `TextControl`: авто/обрезать/заполнить/перенос/красным |
| 0x1B | `bType` (`byte`) | `ContentType` (см. ниже): `0`=текст, `1`=выражение, `2`=шаблон, `3`=фиксированный шаблон |
| 0x1C | `bAllowEdit` (`bool`) | |
| 0x1D | резерв (`byte`) | |

После `CSheetFormat`, если версия потока = 7, идёт ещё `text_orientation:int16`
(в версии 6 этого поля нет). Дальше — опционально, только если
соответствующий бит установлен во `dwFlags`:
- `FLAG_TEXT` (`0x80000000`) → `CString text` — видимый/печатаемый текст
  **или**, в зависимости от `bType`/`FLAG_TYPE` (см. ниже), выражение/шаблон,
  подставляемые 1С при печати;
- `FLAG_VALUE` (`0x40000000`) → `CString value` — отдельное вспомогательное
  поле, замечено в ~600 ячейках корпуса, используется для привязки ячейки к
  источнику построителя отчёта (переменная цикла, напр. `value="Зн"` при
  `text="СокрЛП(_Зн)"`) — более редкий/специфичный механизм, не путать с
  `bType=1` (выражение) ниже; MCP не предоставляет отдельного управления
  этим полем;
- `FLAG_DATA` (`0x00200000`) → `count` + сырые байты.

`FLAG_ROW_HEIGHT`=`0x400`, `FLAG_COLUMN_WIDTH`=`0x800` определяют, действительны
ли `w1`/`w2` как высота строки/ширина колонки соответственно.

**Тип содержимого ячейки** (`bType`/`ContentType`, действителен только если
установлен `FLAG_TYPE`=`0x00080000` — иначе `bType` игнорируется и ячейка
трактуется как обычный текст) определяет, как 1С интерпретирует `text` при
печати. Подтверждено на корпусе `work/ExtForms/*.ert` (~12000 непустых
текстовых ячеек):
- `0` — Текст: `text` выводится как есть (большинство ячеек, `FLAG_TYPE`
  часто вообще не установлен — это подразумеваемое значение по умолчанию);
- `1` — Выражение: `text` — это имя реквизита/переменной 1С (например
  `"Наименование"`, `"ПоставщикОКПО"`), 1С вычисляет и подставляет значение
  при печати; в корпусе почти всегда идёт с явным `FLAG_TYPE`;
- `2` — Шаблон: `text` — литеральная строка с плейсхолдерами
  `[Выражение]` внутри (например `"Всего отпущено [Ном #ЧП] наименований"`),
  1С вычисляет только то, что в скобках, остальной текст выводится как есть;
  необходим для шапок/подвалов большинства реальных печатных форм;
  в корпусе тоже всегда с явным `FLAG_TYPE`;
- `3` — Фиксированный шаблон: как `2`, но вычисляется 1С один раз, а не при
  каждом выводе секции; в корпусе `work/ExtForms` не встретился ни разу
  (0 ячеек), но формат его предусматривает.

С 2026-09 `moxel_writer.simple_table`/`create_ert_file`/`update_ert_print_form`
позволяют задавать тип `1`–`3` для любой ячейки — см. §10.4.

**`LOGFONT`** (`moxel_model.Font`) — 60-байтная структура: 4×`int32`
геометрии + `int32 lfWeight` + 8×`byte` (курсив/подчёркивание/зачёркивание/
кодировка/точность/качество/семейство) + 32-байтное ANSI-имя шрифта
(`fFaceName`).

**Встроенные объекты** (`Objects`) — `DataCell` (формат ячейки-контейнера) +
40-байтная структура `Picture` (тип объекта и его позиция в
колонках/строках/пикселях) +, только для типов `Picture`(5)/`Ole`(4),
дополнительный бинарный payload (сжатое изображение/сериализованный OLE-объект
через `IStorage`). Тип `Text`(3) (текстовый блок без содержимого — судя по
всему используется как декоративная рамка/подложка) и типы `Line`(1)/
`Rectangle`(2)/`None`(0) не имеют дополнительного payload после `Picture`.

### 10.3. Верификация

Разбор (`moxel_reader.parse_moxel`) проверен на **всех 311 файлах**
`Page.1`, найденных в `work/ExtForms/*.ert` — **311/311 успешно
распознаются**, включая реальные печатные формы (ТОРГ-12, товарные
накладные, этикетки, аналитические отчёты) с сотнями непустых ячеек и
десятками встроенных объектов. Запись (`moxel_writer.write_moxel`)
проверена на всех файлах без встроенных объектов (294 из 311, у остальных
17 запись объектов сознательно не реализована — см. 10.4): результат
**структурно идентичен** оригиналу для всех 294 (каждая ячейка после
цикла разбор→запись→разбор совпадает с исходной), и **побайтово идентичен**
оригиналу для 286 из них — на пустом файле (147 байт, самый частый случай:
обработки без визуального отчёта) писатель воспроизводит 1С-файл
**побайтово точно**.

Оставшиеся ~2 байта расхождения на конце потока (см. 10.2) наблюдались во
всех файлах одинаково — `\x00\x00` — и writer их тоже эмитирует, поэтому
на практике расхождений в размере нет; отдельно в 3 файлах (разные версии
одной обработки «КнигаДоходовИРасходов») после этого трейлера встречается
ещё 18 непонятных байт (`00 00 05000000 04000000 08000000 04000000`) —
похоже на следы пересохранения более новой версией 1С, не воспроизводится
писателем и не мешает распознаванию остального содержимого.

### 10.4. Что поддерживает писатель

`moxel_writer.write_moxel` пишет полную структуру MOXCEL (шрифты,
колонтитулы, объединения, секции, разрывы страниц, именованные области),
но **отказывается** (`MoxelWriteError`), если у листа есть `objects`
(встроенные картинки/OLE/линии/рамки) — их сериализация не реализована
(двоичный формат `Picture`+payload понятен на чтение, но писать валидный
OLE-`IStorage`/сжатое изображение в этом проекте не требовалось).

Для MCP используется только помощник `moxel_writer.simple_table(rows,
column_widths=None, row_heights=None)` — строит `MoxelSheet` из плоской
сетки `rows[i][j]`, без какого-либо форматирования, кроме типа содержимого
и ширины/высоты. Каждая ячейка сетки — либо строка (обычный текст,
`bType=0`), либо словарь `{"text": ..., "type": "text"|"expression"|
"pattern"|"fixed_pattern"}` (см. семантику типов в §10.2); при `type`
отличном от `"text"` писатель выставляет `bType` и `FLAG_TYPE`, как это
делает сам 1С в реальных формах. Пустая строка/пустой `text` в сетке — это
отсутствующая ячейка (как и у самого 1С), а не пустой текст. `value`/
`FLAG_VALUE` (см. §10.2) этим помощником не заполняется — он не поддержан
MCP. `column_widths[j]`/`row_heights[i]`, если заданы (и не `0`), пишут
`Columns[j]`/`Rows[i].format` с `FLAG_COLUMN_WIDTH`/`FLAG_ROW_HEIGHT`
(`w2`/`w1` соответственно) — колонка/строка без явного значения получает
подразумеваемую по умолчанию ширину/высоту (`40`/`45`, см. `def_format`
листа и `Moxel.GetColumnWidth`/`GetRowHeight` в источнике-первоисточнике).

- `create_ert_file(..., print_form_rows=[[...],[...]], column_widths=[...],
  row_heights=[...])` — строит начальную печатную форму для новой
  обработки этой сеткой (по умолчанию, без `print_form_rows`/
  `column_widths`/`row_heights`, форма пустая — как и у большинства
  обработок в корпусе образцов).
- `update_ert_print_form(name, rows, column_widths=None, row_heights=None)`
  — заменяет `Page.1` существующей edit-path-обработки на новую сетку
  (остальные потоки не трогаются). Так как это полная пересборка листа
  через `simple_table`, она стирает ранее заданные секции и
  ширины/высоты, заданные точечными инструментами ниже — вызывать её
  нужно до их настройки.

Отдельно, без пересборки всей сетки ячеек, поддерживается точечное
управление:
- именованными секциями (`VerticalSections`/`HorisontalSections`,
  см. §10.2) через `ert_writer.get_editable_print_form`/
  `update_ert_print_form_sheet` и MCP-инструменты `list_ert_print_form_sections`
  (чтение, любая обработка), `add_ert_print_form_section`,
  `update_ert_print_form_section`, `remove_ert_print_form_section`
  (изменение, только --edit-path);
- шириной колонки/высотой строки через `set_ert_print_form_column_width`/
  `set_ert_print_form_row_height` (только --edit-path) — правят
  `sheet.columns[j]`/`sheet.rows[i]` точечно (расширяя `n_columns`/
  `n_rows`, если индекс выходит за текущий размер таблицы) и пишут лист
  обратно тем же `update_ert_print_form_sheet`.

Все эти инструменты читают существующий `MoxelSheet` целиком, меняют
только нужное поле и пишут лист обратно, поэтому остальные ячейки/секции/
размеры не затрагиваются. `AreaNames`/`MoxelArea` инструментами не
поддерживаются (см. §10.2 — не подтверждены на реальном корпусе).

### 10.5. Чтение печатной формы

`get_ert_print_form(name)` (доступен для любой обработки, не только из
`--edit-path`) выводит непустые текстовые ячейки по строкам вида
`строка N: колонка=текст; колонка=текст; ...` (с суффиксом `[expression]`/
`[pattern]`/`[fixed_pattern]` для нетекстовых ячеек, см. §10.2), явно
заданные ширины колонок/высоты строк отдельными строками, плюс количество
размеров таблицы и встроенных объектов (без их детального разбора).
Полезно, чтобы понять, есть ли у обработки печатная форма вообще и что в
ней уже выведено/привязано, прежде чем менять её через
`update_ert_print_form`/точечные инструменты выше.
